# Публикуване и експлоатация

## Избор на платформа

Изисквания: постоянно работещ backend с WebSocket, отделен фонов процес, PostgreSQL, тайни, логове, резервни копия, възможност за мащабиране.

|                         | Render                                                   | Railway                  |
| ----------------------- | -------------------------------------------------------- | ------------------------ |
| Уеб услуга с WebSocket  | да                                                       | да                       |
| Фонов worker            | да (Background Worker)                                   | да (отделна услуга)      |
| Управлявана PostgreSQL  | да, с автоматични копия на платените планове             | да (с volume копия)      |
| Инфраструктура като код | `render.yaml` (Blueprint)                                | `railway.json` за услуга |
| Безплатен вариант       | уеб услугата заспива; worker и база изискват платен план | кредит/пробен период     |

**Избор: Render** (Blueprint описва и трите компонента в един файл; временен адрес `*.onrender.com`; health checks). Цените и ограниченията на плановете се променят – проверете актуалните условия преди стартиране. Railway е равностоен вариант: същият Dockerfile, командата на worker-а се задава в настройките на услугата.

> Публикуването **не е извършено** от тази среда – нужни са акаунт, свързано GitHub хранилище и избор на план (плащане). Конфигурацията е готова; стъпките са по-долу.

## Безплатен вариант (текущият `render.yaml`)

- Една уеб услуга `urbanica` (план **free**): API + клиент + **симулацията в същия процес** (`EMBEDDED_WORKER=true`), и база `urbanica-db` (план **free**).
- Ограничения на безплатния план (проверете актуалните условия в Render): услугата **заспива след ~15 минути без посетители** – тогава светът спира; при следващо отваряне се събужда за ~1 минута и наваксва пропуснатите дни (ограничено). Безплатната база **изтича след около месец**, ако не се смени с платен план.
- CORS: ако `CORS_ORIGINS` не е зададена, се използва публичният адрес, който Render подава автоматично (`RENDER_EXTERNAL_URL`).
- Проверено локално: `npm ci` + `npm run build` в чисто копие от GitHub без `.env`; API с `EMBEDDED_WORKER=true` наваксва и тиктака по часовника. Самият Docker образ не е билднат локално (няма Docker на машината) – билдът става в Render.

**Платен вариант (винаги онлайн):** в `render.yaml` сменете плановете на `starter` (уеб) и `basic-256mb` (база), премахнете `EMBEDDED_WORKER` и добавете услуга `type: worker` със същия Dockerfile и `dockerCommand: node apps/worker/dist/main.js`.

## Стъпки (Render)

1. Качете хранилището в GitHub (Git е инициализиран локално).
2. Render → **New → Blueprint** → изберете хранилището. Render чете `render.yaml` и създава: `urbanica-db` (PostgreSQL 17) и `urbanica` (Docker, health check `/api/health`; симулацията е вътре).
3. `CORS_ORIGINS` не е задължителна – използва се автоматично адресът от Render.
4. Първото стартиране на `gce-api` изпълнява `prisma migrate deploy` и създава света (`ensureWorld`).
5. Проверка: `GET https://<адрес>/api/health` → `{"status":"ok","db":"ok","tick":…}`; `simulationLagMs` трябва да е около 0 (≤ интервала), което потвърждава, че worker-ът тиктака. Отворете адреса и основете град (играчът се създава автоматично).

## Променливи на средата

| Променлива                   | Задължителна    | Описание                                                             |
| ---------------------------- | --------------- | -------------------------------------------------------------------- |
| `DATABASE_URL`               | да              | PostgreSQL връзка                                                    |
| `PORT`                       | не (3000)       | порт на API                                                          |
| `NODE_ENV`                   | да в production | `production` изключва dev функциите                                  |
| `CORS_ORIGINS`               | да в production | разрешени origin-и, разделени със запетая                            |

| `WORLD_SEED`                 | не              | seed на света – използва се само при първото създаване               |
| `RATE_LIMIT_PER_MIN`         | не (300)        | глобален лимит на IP                                                 |
| `DEV_EXPOSE_RESET_TOKEN`     | не              | само разработка                                                      |
| `LOAD_TEST_DISABLE_THROTTLE` | не              | само извън production                                                |
| `REDIS_URL`                  | не              | запазена за бъдещо хоризонтално мащабиране (не се използва в алфата) |
| `WEB_DIST`                   | не              | път до билднатия клиент (по подразбиране `apps/web/dist`)            |
| `PRISMA_LOG`                 | не              | `1` = логване на заявките                                            |

## Логове и наблюдение

- API и worker пишат структурирани JSON редове в stdout (видими в таблото на платформата). Worker: по един ред на тик с продължителност и фази; предупреждение, ако тикът наближи интервала.
- `GET /api/health` – база, латентност, текущ тик, изоставане на симулацията (`simulationLagMs`).
- `GET /api/metrics` – брой заявки, грешки, средно време, бавни заявки, WebSocket връзки, памет, най-натоварени маршрути, продължителност на последните тикове по фази.
- `TickRun` в базата пази историята на тиковете.

Препоръчани аларми: `/api/health` ≠ 200; `simulationLagMs` > 3 × интервала (worker спрял/задръстен); дял 5xx > 1%; продължителност на тик > 50% от интервала.

## Резервни копия и възстановяване

1. **Автоматично:** включете ежедневните копия на управляваната база (Render: платени планове с point-in-time recovery).
2. **Логическо копие на приложението:** `DATABASE_URL=<prod> npm run db:backup` (gzip JSON, консистентен снимък). Съхранявайте извън платформата.
3. **pg_dump** (в Docker образа има `postgresql-client`): `pg_dump -Fc "$DATABASE_URL" > gce.dump`.

Възстановяване:

1. Спрете `gce-worker` и `gce-api` (или ги поставете в режим на поддръжка).
2. Уверете се, че схемата е на същата миграция (`npm run db:migrate`).
3. `node scripts/db-restore.mjs <файл> --yes` (или `pg_restore --clean -d "$DATABASE_URL" gce.dump`).
4. Стартирайте API, после worker-а; проверете `/api/health` и инвариантите (`node -e` с `checkInvariants` или econ-sim срещу копие).

Процедурата с логическото копие е проверена автоматично (`tests/integration/backup.test.ts`).

## Реакция при проблеми

| Симптом                              | Действие                                                                                                                                                                      |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Тикът се проваля (лог `tick failed`) | Worker-ът повтаря с експоненциално изчакване (до 30 s). Фазите са идемпотентни – след поправка продължава от прекъснатото място. Прегледайте стека в лога и `TickRun.phases`. |
| `simulationLagMs` расте              | Проверете дали worker-ът работи и има лиз (`WorkerLease`); при продължителни тикове – увеличете `TICK_INTERVAL_MS` или ресурсите.                                             |
| Два worker-а                         | Безопасно – само притежателят на лиза тиктака; другият чака.                                                                                                                  |
| Изоставане след дълъг престой        | Worker-ът наваксва до 50 тика, после пренастройва часовника (без "лавина").                                                                                                   |
| Съмнение за финансова грешка         | Изпълнете проверката на инвариантите; регистърът позволява пълна реконструкция на всеки баланс.                                                                               |

## Нова версия и миграции

1. CI (`.github/workflows/ci.yml`): lint, формат, build, миграции, тестове, econ-sim.
2. Миграциите са само добавящи; разрушителните промени – на две версии.
3. Render прави rolling deploy на API; миграцията се изпълнява при стартиране на новия контейнер. Worker-ът се рестартира след API.
4. При неуспех: rollback към предишния образ в Render; миграциите не се връщат автоматично – затова са обратно съвместими.

## Управление на тайни

Никакви тайни в Git (`.env` е игнориран). Production стойностите са в настройките на платформата; ротация на `DATABASE_URL` паролата – от таблото на базата, след което рестарт на услугите.
