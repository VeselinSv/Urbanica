# Архитектура

## Обзор

**Модулен монолит + отделен симулационен worker**, споделящи един и същ домейн слой и една PostgreSQL база.

```text
 Браузър (React + PixiJS)
   │  REST /api/*  (намерения за действия)          WebSocket /socket.io (събития)
   ▼                                                        ▲
 apps/api  (NestJS: валидиране, автентикация, права, rate limit)   │
   │  извиква                                              │ LISTEN gce_events
   ▼                                                        │
 packages/domain  (бизнес операции в DB транзакции) ──── pg_notify ──┘
   │  използва чисти функции                                 ▲
   ▼                                                        │
 packages/game-simulation · economy-engine · world-generation · shared
   ▲
   │  същият домейн слой
 apps/worker  (централен часовник, тикове, лиз за единствен лидер)
   │
   ▼
 PostgreSQL  (единствен източник на истина)
```

**Отклонение от примерната структура:** `validation` и `config` не са отделни пакети, а модули в `shared` (`validation.ts`, `balance.ts`, `catalog.ts`) – клиентът и сървърът ги ползват заедно и разделянето би добавило само конфигурация. Добавен е `packages/domain` – слоят, споделян от API и worker, без който би имало дублиране на бизнес логика.

## Поток на действие на играча

1. Клиентът изпраща **намерение** (напр. `POST /api/cities/:id/build {action:'road', tiles}`) с `Idempotency-Key`.
2. API: AuthGuard (сесия) → ThrottlerGuard → zod валидиране → домейн функция.
3. Домейнът в транзакция: `SELECT … FOR UPDATE` на града → проверка на собственост, територия, терен → изчисляване на цената → `transfer()` в ledger → запис на новите плочки, `version++` → `IdempotencyRecord`.
4. При commit клиентът получава резултата; ако има `pg_notify`, шлюзът разпраща събитие.

Клиентът никога не определя пари, собственост, наличности, цени или резултати – само ги показва.

## Симулационен процес (worker)

- **Централен часовник:** `World.tick`, `World.lastTickAt`, `World.tickIntervalMs` (конфигурируемо с `TICK_INTERVAL_MS`). Един тик = един игрови ден. Няма разпръснати таймери в модулите.
- **Единствен лидер:** таблица `WorkerLease` (лиз с TTL 30 s). Няколко worker инстанции са безопасни – само една тиктака.
- **Фази на тика** (`packages/domain/src/simulation.ts → processTick`):
  1. `cities` – чистата `stepCity` се изчислява извън заключване; записът е с оптимистична проверка на `version` и `lastTick` (редакция на играча междувременно → преизчисляване).
  2. `companies` – производство, заплати, поддръжка, такси, изследвания, лицензи (по една транзакция на компания, `lastTick`).
  3. `logistics` – пристигащи доставки, падежиращи договори.
  4. `market` – градско потребление, световен внос/износ, нови референтни цени, история.
  5. `finance` – вноски по кредити, изтичане на предложения.
  6. `reports` – дневни отчети на компаниите, месечен корпоративен данък, рейтинги, макро (ценови индекс, базова лихва), почистване на стар чат.
- **Възстановяване след срив/рестарт:** всяка фаза е идемпотентна (`lastTick` маркери, уникални ключове в ledger, `nextDueTick`, история на цените по `(instrument, tick)`). Ако процесът спре по средата, следващото изпълнение довършва само пропуснатото. Пропуснатите тикове се наваксват (до `maxCatchUpTicks`, после часовникът се пренастройва).
- **Адаптивна симулация:** градове на неактивни играчи (без заявка 15 мин) се обработват на пакети от 5 дни с `stepCityDays` – **същата** дневна функция, изпълнена N пъти в паметта, с един запис. Резултатът е математически идентичен (покрито от unit тест). При повторно активиране натрупаните дни се изчисляват в правилния ред.

## Комуникация в реално време

API процесът държи постоянна `pg` връзка с `LISTEN gce_events`. Worker-ът и API-то публикуват събития с `pg_notify` вътре в транзакциите – доставят се само при commit. Шлюзът ги маршрутизира към стаи: `world` (тик, пазар), `user:<id>` (известия, промени в града), `chan:<канал>` (корпоративен/съюзен чат след проверка на правата). Това позволява няколко API инстанции без Redis.

## Решения за производителност

- Теренът не се пази в базата – генерира се детерминистично по чанкове (32×32) на клиента; сървърът пази само промените.
- Пространственото състояние на града е версиониран JSON документ (`City.tiles`), а икономическите обекти – релационни. Една симулационна стъпка = един запис на града.
- Клиентът рисува чанкове с кеширане и LOD (груби чанкове 4×4 при отдалечаване), сградите на един град са в един `Graphics`, сортиран по дълбочина. Регионите се зареждат до 256×256 плочки.
- Индекси за всички често филтрирани колони (виж docs/database).
- Пакетна (обобщена) симулация за неактивни градове.

## Защо без Redis в алфата

- Опашките са излишни: тикът е детерминистичен цикъл с идемпотентни фази, а лизът и `pg_notify` покриват координацията.
- Ограничаването на заявките е в паметта на процеса (достатъчно за една инстанция).
- При хоризонтално мащабиране на API: Redis за `@nestjs/throttler` storage и socket.io adapter (`REDIS_URL` е запазена променлива). Документирано като следваща стъпка – не е реализирано, защото не може да бъде проверено в текущата среда.

## Мащабиране – измерено и следващи стъпки

Измерено локално (виж docs/testing): 40 града + 39 компании ≈ 5,3 s на тик последователно. Горещото място е системната сметка `system:world`, която участва в повечето парични потоци и сериализира транзакциите. План: (1) шардиране на системните сметки (`system:world:0..15`), (2) паралелна обработка на градовете по региони, (3) пакетни вмъквания в ledger, (4) отделни worker-и по региони на света с лиз за регион.
